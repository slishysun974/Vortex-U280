# Iris 三分类在 Vortex-U280 上的端到端验证计划

2026-11-23 · 设计稿 v1.0。下文保留开工前的计划和当时状态。实施后四路各通过 9/9，正式结果、逐行预测及复现命令见[实验报告](IRIS_U280_RESULTS_20261123.md)。

**本项目用一个新的整数 PTX 内核完成真实数据的三分类推理。**CPU 从训练集学习三个类别中心，U280 读取测试特征和模型参数，自行计算距离、选择类别并写回结果。最终应能从一条预测追溯到原始样本、独立答案、PTX 源码、所加载的镜像和实卡回读字节。

前期讨论已用公开数据取得 CPU 参考值。正式数据冻结、新内核构建、SimX、处理器 RTL、NOXRT AFU 和物理 U280 执行均为 `NOT_RUN`。既有 P0 板测说明底层路径具备实施基础。Iris 的运行结果须由本项目单独取得。[已有四路验收](E_RUNTIME_UNSEEN_ACCEPTANCE.md)

## 1. 完成条件

| 新 PTX 能否在自研链路上运行？ | 同一份 PTX 经正式前端和固定工具链生成仿真模块与实卡模块，各自通过装载前校验。记录实际命令、退出码、目标锁、模块和镜像哈希。 |
| U280 是否正确执行了推理？ | 45 个测试样本的 **135 个整数距离和 45 个预测类别**逐字与独立答案一致，输入、模型、输出保护区核验通过。训练集拟合和准确率统计均在 CPU 完成。 |
| 结果对哪些情况成立？ | SimX、处理器 RTL、NOXRT AFU、物理 U280 分别完成第 5 节的固定用例，独立列出状态。主实验只评价固定配置下的整数推理功能，性能和板端训练可另立课题。 |

## 2. 数据、训练和独立答案

**数据源与划分。** 选用 R. A. Fisher 的 UCI Iris 数据文件 `bezdekIris.data`，150 行、每类 50 行。特征顺序固定为花萼长度、花萼宽度、花瓣长度、花瓣宽度。类别编号依次为 `0=setosa`、`1=versicolor`、`2=virginica`。保留原文件字节与原始行序，记录 SHA-256、获取日期和来源，随分发材料保留作者及 CC BY 4.0 署名。[数据集与许可](https://archive.ics.uci.edu/dataset/53/iris) · [指定数据文件](https://archive.ics.uci.edu/ml/machine-learning-databases/iris/bezdekIris.data)

1. 每类内部从 0 编号，序号模 10 的余数为 0、3、7 时分入测试，其余分入训练。导出按原文件顺序排列的两份行号清单，验证两者无交集且并集覆盖 150 行。每类训练 35、测试 15，合计 105/45。
2. 将原始十进制厘米读成整数毫米，例如 5.1 cm 转成 51 mm。按十进制文本精确转换。输入域定为 0 至 100 mm。各维度使用原单位和相同权重。
3. 对训练集中每个类别、每个特征求和，得到 `S[3][4]`。训练过程只读取训练行。设备输入为特征和这 12 个数，真实标签保存在主机验收端。
4. 答案生成器按数学定义、用有理数表示类别均值，求样本到均值的平方距离，再乘以 1225 得到应写回的整数。并列最小值取最小类别编号。独立实现只依赖数据文件和此定义。在首次设备执行前冻结输入、答案、类别映射及文件哈希。

**设计阶段的 CPU 校对值。** 下表供实施时排查数据版本、字段顺序或划分错误。正式实验须从原始文件重算。混淆矩阵行是真实类别，列按 0、1、2 排列。

| 类别 | 四个训练特征和，单位 mm | 测试预测数，依次为 0、1、2 |
|---|---|---|
| 0 | 1753，1199，511，86 | 15，0，0 |
| 1 | 2093，988，1489，470 | 0，12，3 |
| 2 | 2302，1032，1940，712 | 0，2，13 |

例如，第一个测试样本为 `[51, 35, 14, 2]` mm，CPU 参考的三个缩放平方距离为 `[2397, 1309034, 2819202]`，预测为 0。5 个模型误分类样本同样纳入设备核对。

## 3. 设备内核与数值设计

拟新增单入口 `iris_nearest_centroid_u32`，输入为 PTX 7.0、`sm_70`、64 位地址。一个逻辑线程处理一行样本，一个内核启动完成整批分类。模型通过设备缓冲区传入，同一份设备镜像可接受不同模型参数。[现有 P0 指令白名单](../configs/ptx_frontend/v1/profile.json) · [PTX 兼容性规范](PTX_COMPATIBILITY_PROFILE.md)

将样本的第 `j` 个特征记为 `x[j]`。类别中心是 `S[c,j] / 35`。内核比较以下整数距离，三类共用相同缩放因子，故与精确均值的分类结果一致。

```text
D[c] = Σ (35 × x[j] − S[c,j])²       j = 0,1,2,3
输出 = [D[0], D[1], D[2], 最小距离对应的类别编号]
```

- **线程与地址。** 由 `%ctaid.x × %ntid.x + %tid.x` 算出样本序号 `i`。用 `mul.wide.u32` 计算 16 字节行偏移，使用 `add.u64` 加到设备基址。所有样本、模型的全局读取及结果写入均受 `i < n` 保护。临时寄存器先定义，再进行带谓词的读取，符合现有前端的初始化检查。
- **整数算术。** 将 3 类 × 4 特征显式展开。对每个特征先比较 `35*x` 和 `S`，用 `sub.u32` 和 `selp.u32` 取得非负差，再用 `mul.lo.u32` 平方、`add.u32` 累加。允许域中两个被减数均在 0 至 3500，单个距离上界为 `4 × 3500² = 49,000,000`，可用 u32 精确表示。
- **类别选择。** 初始赢家为类别 0，依次比较 1 和 2，仅在新距离严格较小时更新赢家及当前最小距离。使用 `setp.lt.u32` 和 `selp.u32`。三项距离和最终类别均由设备写回，PTX 末尾执行无条件 `ret`。

## 4. 主机、内存、构建与实卡接口

**启动参数。** 采用现有小端 `ptx-vx-args-v1`。三个地址由项目 runtime 从 `BufferSlice` 解析。下表是计划布局，构建后以源码产生的 manifest 逐项交叉核对。[合作接口](COLLABORATION_PROTOCOL.md) · [启动参数检查](../scripts/ptx_launch.py)

| 参数 | 类型／payload 偏移 | 设备数据与读写约定 |
|---|---|---|
| `x` | u64 指针／0 | 只读，行优先，每样本连续 4 个 u32，步长 16 B |
| `sums` | u64 指针／8 | 只读，类别优先，每类连续 4 个 u32，共 48 B |
| `out` | u64 指针／16 | 只写，每样本连续 4 个 u32，依次为三个距离、一个类别，步长 16 B |
| `n` | u32 标量／24 | 本次样本数，字节 28–31 填零，payload 共 32 B |

**缓冲区与调度。** 使用三份独立、4 字节对齐的分配。主实验 `block=(32,1,1)`，`grid=(2,1,1)`。通用用例令 `G=max(1,ceil(n/B))`，`x/out` 各留出 `G×B` 行物理空间，三份分配前后各设 16 B 保护区。传给设备的地址指向数据区首字节。分配、非零偏移、逻辑范围和保护区分别记入清单。主机声明的 `x/out` 访问长度为 `16*n`，`sums` 为 48 B。即使 `n=0` 也传入有效地址并实际启动一个块。主机检查输入长度、值域和模型范围之后再提交。

每次用确定且可区分的字样填充输入尾部和输出保护区，输出数据区预置为区别于合法结果的值。通过 `Context` 分配、写入、装载、启动、等待完成，再回读三份完整分配。45 样本时输出数据区的前 720 B 应等于答案，余下 19 行及两端保护区应逐字节保持初值。记录运行前后的输入和模型全区、实际设备地址和启动 payload。[运行时入口](../scripts/ptx_runtime.py)

**构建目标。** 使用固定 WSL `Vortex-AB-Ubuntu-22.04` 中的源码与工具链，源身份按根 lock 核对。模型使用 D5 的 1 核、8 个 warp、每 warp 4 线程配置。实卡使用 U280 专用 lock、D10 xclbin 与 D12 主机库。分别在新目录执行 `ptx_module.py prepare → build → validate`。首版使用默认 v1.2 前端、逐字节参数读取和通用板用模块格式。v1.4 对齐优化有单独的六镜像准入契约。这里构建的是新 kernel 的 `vxbin`，FPGA 继续使用固定 D10。[根 lock](../configs/target_lock.json) · [模型 lock](../configs/candidates/block32-v1/target_lock.json) · [实卡 lock](../configs/candidates/u280-hbm32-v1/target_lock.json) · [模块构建器](../scripts/ptx_module.py) · [参数读取契约](PTX_DEVICE_PARAMETER_ACCESS.md)

**实卡运行。** B/C 在可用的设备窗口按现有 BoardGate 核对当次 BDF/index、shell、空闲状态、HOST 容量、镜像 UUID、D12 身份和实际 200 MHz，使用板用模块及 `u280-xrt` binding。设备端只接收执行所需的输入、参数及镜像。原始回读传回后由验收端比较。保留板端、传输及本地核验三个退出码。设备超时或状态不确定时，保存首个错误和已采集的原件，按现有物理恢复边界处理。[实卡门禁](../scripts/ptx_u280.py) · [运行与传回先例](D_P0_CLOSEOUT.md) · [物理恢复边界](RUNTIME_RECOVERY_20261111.md)

供实施时参考，两个目标的 `prepare` 分别配套 `block32-v1/native_smoke.json` 和 `u280-hbm32-v1/fpga.json`。三个构建子命令的参数如下。运行者在固定 WSL 的项目根目录设置每个目标独立的目录和变量，并从固定工具链记录取得 `VORTEX_SOURCE`、`TOOLDIR`。已有 V03 驱动绑定专用语料和模块哈希，Iris 只复用其中的构建调用与取证方式。[双目标构建先例](../scripts/build_ae_v03.py)

```sh
python3 -B scripts/ptx_module.py prepare "$PTX" --output "$MODULE_DIR" --hardware "$HARDWARE" --target-lock "$TARGET_LOCK"
python3 -B scripts/ptx_module.py build "$MODULE_DIR" --build-root "$BUILD_DIR" --vortex-source "$VORTEX_SOURCE" --tooldir "$TOOLDIR" --target-lock "$TARGET_LOCK"
python3 -B scripts/ptx_module.py validate "$MODULE_DIR" --target-lock "$TARGET_LOCK"
```

## 5. 用例矩阵与判定

每个后端使用同一份冻结的用例清单和答案。下表共 **9 次启动／后端**，四路各自记录 9 个结果。真实数据批次均按第 2 节的测试行序选取。表中 45 样本一行单独用于报告模型准确率，其他启动用于验证工程行为。

| 用例 | 数据、模型和启动 | 检查重点 |
|---|---|---|
| 正式测试，1 次 | 原模型，45 个测试样本，B=32 | 核对 135 距离、45 类别、混淆矩阵和 19 行尾部 |
| 空批与单样本，2 次 | 原模型，N=0 和 N=1，B=32 | 空批整份输出保持初值。单样本复核第 2 节算例 |
| 块边界，3 次 | 原模型，测试集前 31、32、33 行，B=32 | 块末、整块和第二块首样本，检出索引或尾部谓词错误 |
| 更换模型，1 次 | 测试集 45 行，同一模块把模型行换为原顺序 [1,2,0]，B=32 | 距离列和赢家编号随**运行时传入**的模型变化，检出硬编码中心或标签 |
| 并列距离，1 次 | 人工中心 (0,0,0,0)、(2,0,0,0)、(0,2,0,0)，按 35 倍传入。输入 (1,1,0,0)、(2,2,0,0)，B=32 | 第一行三类同距，选 0。第二行类别 1、2 并列且优于 0，选 1 |
| 数值端点，1 次 | 三类中心的四维分别全 0、全 100、全 50，按 35 倍传入，输入全 0、全 100，B=32 | 覆盖零距离、两个减法方向以及最大距离 49,000,000 |

每次均检查事件完成、距离、类别、输入与模型全区、输出有效区和保护区。使用 Python 任意精度整数或有理数逐项核对，再比较小端序列化结果。任何差异报告后端、用例、原始行号或合成样本号、输出字段、字节位置、期望值和实测值。验收脚本另用保存的回读副本翻转一个距离字、改一个类别、破坏一个尾部字，分别验证能定位并拒绝三种错误。

| 层级 | 本项目要取得的证据 | 计划发布时状态 |

| CPU 正式冻结 | 数据身份、划分、训练值、精确答案、混淆矩阵 | NOT_RUN，已有设计阶段参考值 |
| 前端与模块 | 同份 PTX 的 IR、源映射、参数布局、生成的设备源码、ELF、vxbin、反汇编、构建日志、两套目标身份 | NOT_RUN |

| NOXRT AFU | `xrtsim` 绑定与本层 9 次实跑回读 | NOT_RUN |

## 6. 实施顺序、分工和工期

以下为开工后的排期估算。按 A 架构与执行语义、B 平台、C runtime、D 前端、E 独立验收分配职责。设备窗口等待时间另计。

| 阶段 | 负责人 | 预计投入 | 完成本阶段的交付 |
|---|---|---|---|
| M1　数据和答案冻结 | E | 0.5 人日 | 固定原始数据、划分及署名。按数学定义重算第 2 节，冻结 9 个用例的输入、答案和 manifest |
| M2　内核与双目标构建 | D，A 审核数值和线程语义 | 0.5–1 人日 | PTX、ABI 核对表、两套独立构建目录和验证记录。板用 manifest 能按板用 lock 校验 |
| M3　本地执行与复核 | C 执行，A/E 复核 | 1–2 人日 | 接通统一运行入口，三模型各完成 9 次。负对照均检出，差异保留原始回读并定位 |
| M4　实卡验收 | B/C 执行，E 比对 | 0.5–1 人日及一次板卡窗口 | 固定 D10/D12 下完成板测，将原始回读带回本地，独立核对 9 个结果 |
| M5　演示与交接 | E 汇总，A–D 核对所属层 | 0.5 人日 | 给出模型准确率、各层一致率、已验证边界、失败记录和可复现命令，更新项目状态与交接 |

M1 与 M2 可并行，M3 使用冻结输入和已校验的模型模块。M4 使用同一份冻结输入、已校验的实卡模块和 M3 的核验器。若板卡窗口未落实，本地阶段照常交付，实卡项注明具体外部依赖。实跑后出现算错或启动失败的用例标记 `FAIL`。修正后采用新 run_id 重跑并关联原记录。

**出现差异时的定位顺序**

| 现象 | 首先检查 |
|---|---|
| CPU 得到的训练和或混淆矩阵与第 2 节不同 | 文件名与原始行序、类内编号基数、毫米转换、特征和类别次序。先定位数据差异，再冻结正式答案。 |
| 三个距离算对但类别错误 | 严格小于比较、赢家及最小值是否同步更新、模型换序与平局用例。 |
| 首块正确，第二块或尾部保护值错误 | 逻辑线程号、16 B 行步长、`i<n` 谓词以及 BufferSlice 的有效区偏移。 |
| 本地模型一致，实卡装载失败或输出不同 | 先核对实卡模块和 lock、板用 Python 与运行包依赖、当次板卡门禁。再比较实际 32 B payload、内存初值、完成事件和回读字节，区分装载、传输、执行与回传故障。 |
