# AI 智能体辅助的 Vortex-U280 GPGPU：研究计划与五人分工

版本：`research-v2.0`；日期：2026-11-07；首期：从重新启动日 D1 起 30 天；沿用五人 A—E，姓名待团队填写。

本计划按新的研究方向重制，替代原来的 AEC-G 赛题路线。协议见 [合作接口协议](COLLABORATION_PROTOCOL.md)，编译范围见 [PTX 兼容性规范](PTX_COMPATIBILITY_PROFILE.md)，执行入口见 [启动清单](STARTUP.md)。当前项目仅保留 Vortex 路线；旧 AEC 计划与协议留在原项目归档。本文是实施方案，未把计划中的功能记为已完成。

## 1. 研究定位与成果边界

**建议题目：AI 智能体辅助的开源 GPGPU 协同开发——面向 U280 的 Vortex 定制与 PTX 子集兼容编译。**

目标是基于开源 Vortex 建立团队可修改、可构建、可验证的 GPU 原型，自研受限 PTX 前端和语义转换，将程序编译为 Vortex 所使用的 RISC-V 与 SIMT 扩展指令，在 U280 上执行，并用对照实验评价 AI 智能体的开发效果。

对外准确表述为“基于 Vortex 定制的 GPGPU，支持明确列出的 PTX 子集”。PTX 是虚拟 ISA，不能据此宣称兼容 NVIDIA SASS 二进制、完整 CUDA runtime、cuBLAS/cuDNN 或任意 CUDA/PyTorch 程序。[NVIDIA PTX 文档](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html)

Vortex 官方已列 U280 平台和 RV32/RV64 配置；配套 VOLT 已有 CUDA/OpenCL 编译路线。因此不把“首次让 CUDA 在 Vortex 上运行”或已有核心架构作为原创成果。研究增量放在受限 PTX 输入、语义与接口验证、定制配置，以及智能体协作的可复现实验。[Vortex](https://github.com/vortexgpgpu/vortex)、[VOLT](https://github.com/vortexgpgpu/Volt)

### 1.1 三个研究问题

| 问题 | 实际做什么 | 如何判断 |
|---|---|---|
| RQ1：受限 PTX 能否可靠迁移到 Vortex？ | 自研解析、类型/能力检查、语义 lowering、线程与参数适配 | 已声明子集的正例、边界和拒绝用例；独立答案与设备输出一致 |
| RQ2：明确接口与独立验证的多智能体协作是否有效？ | 比较单智能体与按模块分工的智能体流程 | 同等任务与预算下的正确完成率、人工修复时间、成本、逃逸缺陷 |
| RQ3：兼容层的代价与硬件配置影响是什么？ | 同一 U280 配置比较 PTX 路线和原生 Vortex 路线；再做单变量配置对照 | 代码量/指令数、设备时间、端到端时间、资源、时序；只比较已正确的结果 |

首月优先完成 RQ1 和 RQ2 的小规模证据，RQ3 先形成基线；是否开展硬件优化由闭环进度决定。

### 1.2 首期必做、扩展与暂缓

| 层级 | 范围 | 交付判据 |
|---|---|---|
| 首期必做 | 固定 Vortex/工具链基线；PTX 整数子集；项目 runtime 适配；copy、vadd、整数 affine 三类 kernel | 同一源码经通用编译流程；SimX 和 RTL 验证；具备板卡条件时完成 U280 实测 |
| 首期系统目标 | 真实 U280 运行上述 kernel，记录构建/时序/输入输出证据 | 仿真通过、板上通过分开记录；没有板上证据就不能宣布 U280 目标完成 |
| 条件扩展 | 结构化分支、FP32；随后再做 shared memory/barrier、reduction、简单 GEMM | 每个扩展先更新 profile、测试和验收，不靠“大概兼容”纳入承诺 |
| 后续研究 | 一项硬件或访存配置优化，更多 PTX 与 CUDA 生成样例 | 与冻结基线对照；报告收益和代价 |
| 不列首月必做 | FP8/MMA、完整 PyTorch 后端、ResNet/LLM、全 CUDA API、SASS、从零开发 PCIe/HBM 控制器 | 后续另立工作包 |

赛题的固定 AEC ISA/API、FP8 必选、固定 HBM 通道数和模型评分不再约束本研究。若未来参赛，另做合规差距表；本计划不代表满足原赛题。

## 2. 技术路线与复用原则

```text
受限 PTX 文件（先手写合法样例，后接固定 CUDA 工具链输出）
  → 自研解析器 / 类型与能力检查
  → 有类型的 PTX IR：线程、谓词、地址空间、位宽均显式保留
  → 语义 lowering + Vortex 线程/参数适配
  → 配套 Vortex/VOLT 的 LLVM/SIMT 后端、链接器和打包工具
  → 模块包：Vortex 可加载程序 + manifest + 参数说明 + 调试映射
  → 项目 runtime 适配层 → 固定版本 Vortex runtime
  → SimX / RTL 仿真 / U280 XRT 后端
  → 独立答案比较、错误诊断、性能与 AI 开发证据
```

这里的“自研编译器”包括 PTX 前端、类型检查、语义转换、诊断、模块描述和验证工具；寄存器分配、指令选择、SIMT 分歧处理和链接优先复用已验证后端。PTX 到 RISC-V 不能只做 opcode 字符串替换。普通 LLVM RISC-V 后端也不能自动等同于 Vortex 的专用后端。

第一阶段可以由 PTX IR 生成受限 C/C++，再走配套 Vortex 编译器，前提是显式实现位宽、无符号溢出、谓词访存和线程语义，并保留自动转换链路。此时如实称为“PTX 转译前端”；不是人工重写每个 kernel。中期再按需要直接生成 LLVM IR，不在同一月同时维护两条完整后端。

### 2.1 两条并行基线

1. **硬件基线**：上游原生 kernel → 上游工具链/runtime → U280。A/B/C 先证明平台与原生 Vortex 可用。
2. **兼容基线**：同一运算的 PTX → 自研前端 → 同一后端/runtime → SimX/RTL。D/E 不等待 bitstream 开发。

两条基线使用同一 target lock，汇合后替换的主要部分是程序生成方式。若原生 kernel 已不能运行，先定位平台；若原生通过而 PTX 失败，优先定位前端、ABI 和线程适配。

### 2.2 第一个版本的关键决策

- 优先尝试 `.address_size 64` 与 RV64 目标，保留 64 位设备地址；实际选择必须由配套工具链、RTL 和 U280 验证。RV32 只能作为另一个显式受限 profile，不能直接丢弃指针高位。
- 首版选择无跨线程通信的整数 kernel；支持 1D grid/block，明确逻辑线程编号。PTX 的线程编号不等于 Vortex 硬件 lane 编号。
- P0 不暴露 warp 相关操作，不因旧赛题强制 Vortex 物理线程宽度为 32；扩展 warp 指令前另行验证完整 32-thread 语义。
- 先验证谓词为假时不访问内存，再扩展分支与收敛；barrier/shared memory 在独立阶段处理。
- 选择能够在本地条件复现的一组 Vortex、配套 LLVM/VOLT、runtime、平台和 FPGA 工具版本。当前上游不同代 runtime/API 有变化，不混用教程、头文件和 bitstream。
- U280 优先沿用上游 XRT 平台流程，C 适配已安装 shell/platform。文档示例的 platform 名称、工具版本和 HBM 映射不能直接当成本机事实。[FPGA 指南](https://github.com/vortexgpgpu/vortex/blob/master/docs/fpga_setup.md)

建议组织为 **2 人硬件与平台 + 2 人编译器 + 1 人验证与应用**，C 兼任软件集成协调人，协调工作不等于承担所有集成缺陷。

| 人员 | 主责 | 首周可交付成果 | 主要交接 |
|---|---|---|---|
| A：Vortex 架构与 RTL | 核心配置、ISA/SIMT 语义、SimX/RTL 基线、分歧与访存问题、定制硬件变更 | 固定配置、原生 kernel 仿真、能力表、RTL 运行入口 | 向 B 交构建配置；向 D 交目标语义与能力；接 E 验证用例 |
| B：U280 平台与实现 | 平台/XRT 环境、FPGA 构建、板卡内存连接、时序资源、上板与计数器 | 平台盘点、构建脚本、原生程序上板路径；无入口时先审查平台配置和构建依赖 | 接 A 的 RTL/配置；与 C 对接传输与完成；向 E 交真实测量 |
| C：编译后端适配与 runtime | LLVM/Vortex 后端接入、模块打包、设备侧启动适配、host API、装载/同步/错误与恢复 | 原生最小程序的统一运行入口、模块 manifest 草案、参数打包样例 | 与 D 固定 IR/ABI；与 B 固定平台运行；给 E 调用 API |

| E：验证、应用与 AI 实验 | 独立 oracle、测试语料、端到端回归、未见 kernel 验收、AI 对照记录、报告 | 三类 kernel 输入/答案/边界；冻结验收集；AI 任务卡 | 给 D 需求；接 C 运行接口；与 A/B 验证功能/性能 |

### 3.1 避免责任重叠

- A 负责“指令如何执行、核心如何请求内存”；B 负责“核心如何接到 U280、数据如何经过平台”；C 负责“应用如何分配/传输/装载/启动”。
- D 负责 PTX 到具有明确语义的目标中间表示；C 负责该表示接入后端和可加载模块。线程/参数 ABI 由 A/C/D 联合维护，E 用独立用例验收。
- A/B 首月不重写现成 ALU、PCIe、HBM 控制器；闭环后再按测量选一个改动。历史 AEC ALU 可保留作局部实验，不强接 Vortex 接口。
- E 维护系统验收和研究实验，每人仍负责自己模块的单元测试、诊断与修复。AI 不能取代人对交付物的责任。

## 5. 验证与性能研究

### 5.1 四层验收

| 层 | 通过证明什么 | 不能据此推断什么 |
|---|---|---|
| 前端/语义单测 | 解析、类型、指令和拒绝行为符合 profile | RTL 或板卡已正确 |
| SimX / 独立参考 | 编译后的程序在声明模型中与答案一致 | 实际 FPGA 时序/带宽/功耗 |
| RTL 仿真 | 目标 RTL 的取指、执行、访存等实际逻辑通过所测用例 | 已完成布局布线或 U280 实测 |
| U280 | 固定 bitstream、配置和环境下真实运行 | 任意 PTX、所有 shape 或其他配置均兼容 |

对照顺序：E 的独立 CPU 算子答案 → 原生 Vortex kernel → PTX 编译 kernel；有 NVIDIA 设备时增加同 PTX 的原厂执行对照，没有则该项记 NOT_RUN。CPU 算子答案只证明该算子的可观察输出，不能替代完整 PTX 语义测试。

最少覆盖：N=0/1/7/31/32/33/63/64/65/257/1024；非整块尾部；零、全 1、最大 u32、溢出、固定随机输入；谓词为假时的越界候选地址不产生访问；非法版本/指令/参数/能力被拒绝；重复启动和错误恢复；通过地址哨兵、trace 或可用的硬件观察验证范围。硬件本身不提供的异常不能在报告中编造为精确 trap。

### 5.2 性能实验

1. 固定输入、算法、编译优化、硬件配置和时钟，比较原生 kernel 与 PTX kernel，隔离兼容前端开销。
2. 首轮采用 5 次预热、30 次测量，报告中位数与范围；RTL 过慢时预先声明较小重复数。记录编译/装载、H2D、kernel、D2H、总时间，不把 host wall time 冒充硬件周期。
3. 可选一个硬件变量，例如 core 数或 cache 配置；每次改变重新生成 bitstream 并验收。比较实现后频率、LUT/FF/BRAM/URAM/DSP 与时间，不只看理论吞吐。
4. 基线性能无预设加速承诺。小 kernel 可能受传输和启动支配；无板上功率读数则功耗为 NOT_MEASURED，仿真周期不能换算为实测能效。

## 6. AI 智能体的使用与对照实验

智能体按交付物分工：资料/架构、PTX 前端、后端/runtime、RTL/平台、独立测试/审查。五位同学分别管理自己模块的任务；同一个人可以调度多个智能体，无需把五人固定成五个聊天窗口。

每张任务卡包含输入、可改文件、目标接口、支持范围、验收命令、禁止改动项、时间/token 预算、产物目录和人类负责人。实施智能体不修改冻结 oracle；审查智能体从规范独立检查，验收由非作者复现。提交日志保留模型标识、提示词/任务卡、代码差异、工具命令、失败轮次、人工修改与最终状态；凭据不进入日志。

**主对照：单智能体 vs 明确接口分工的多智能体。** 建议选择 6 组成对且难度接近的微任务，覆盖前端诊断、谓词 lowering、参数序列化、运行错误处理、RTL 测试和故障定位。随机分配组别、平衡人员熟练度，固定可用工具、资料、总 token/费用和时限；多智能体组所有子任务成本合并计入。

同一人不先完成原题再做另一组同题；采用等价变体降低学习效应。任务开始前冻结验收，保留失败/超时样本；对重复运行报告分布，不挑最佳一次。无 AI 小样本可作补充，但不要拿前期人工搭环境时间与后期 AI 修小 bug 时间直接比较。

| 指标 | 记录方法 |
|---|---|
| 正确完成率 | 时限内通过独立冻结验收的任务数 / 全部任务数；未完成纳入分母 |
| 人工投入 | 阅读、调试、改码、复核的实际分钟数；等待与主动操作分开 |
| 效率/成本 | 端到端耗时、总 token、可获得的实际费用、工具耗时与并行等待 |
| 质量 | 首次接收率、接口缺陷、验收后逃逸缺陷、负例检出情况 |
| 可复现性 | 非作者能否按固定输入、版本和命令重现 |

30 天的小团队实验属于探索性证据，应报告样本量、难度差异和人员影响；不能仅凭代码行数、聊天数量或“感觉更快”得出智能体更有效的结论。

## 7. 风险与范围调整

| 风险 / 触发点 | 负责人与动作 |
|---|---|
| 上游版本不兼容，原生程序跑不通 | A/C 冻结已配套的版本组合；B 核对 U280 平台，不追随每日 master |
| U280 入口/工具/host-memory 条件不具备 | B 列明需要的环境与恢复流程；继续 SimX/RTL，保留板上未完成状态 |
| PTX 语法扩张，D7 尚无 vadd | C/D 缩到已公布 P0，先贯通；不临时堆加 CUDA runtime 或模型 |
| RV64 资源/工具链受限 | A/B/C/D 评估后建立单独 RV32 受限 profile，保留完整地址检查和能力标识 |
| 分歧或 barrier 不可靠 | A/C/D 保持 P0，无跨线程同步；扩展逐项验证，不忽略指令 |
| FPGA 构建耗时、时序不收敛 | A/B 降低核心/缓存规模或频率目标，版本和实验条件随之更新 |
| AI 修改测试让错误通过 | E 保管冻结验收；独立复现、故障注入；人类审查测试变更 |
| 自主贡献表述过度 | E 汇总来源与许可、上游功能、自研改动和未实现项；不将已有功能计原创 |
