# Vortex U280 的 A B 个人执行计划

日期：2026-11-07。依据 [research-v2.0 总计划](RESEARCH_PLAN.md)、[合作协议](COLLABORATION_PROTOCOL.md)、[启动清单](STARTUP.md) 和 [PTX 规范](PTX_COMPATIBILITY_PROFILE.md)。负责人：你，兼任 A 和 B；C/D/E 的职责沿用团队计划。

你的任务是把 Vortex 核心变成一套可复现、可验证的 U280 计算平台，让队友生成的程序能够在上面正确运行。先建立原生程序基线，再接 PTX 编译产物，最后在进度允许时研究一个配置变量。

按实际重新启动日计 D1，首期 30 天；下表是执行安排，平台可用性和阶段验收决定能否进入下一步。截至制定时，[状态记录](STATUS.md) 中 Vortex 版本冻结、SimX、RTL、U280 均为 NOT_RUN。历史 AEC 的局部 ALU 结果只作方法参考。

**A 做什么：确定核心怎样工作，并在仿真中验证。**

可以把 Vortex 看成一套已有的 GPU 电路设计。A 要先选定版本和规模，搞清楚程序如何分给线程、如何计算、如何读写内存，再用小程序检查这些行为。

| 工作 | 通俗解释 | 怎么做 | 留下什么 |
|---|---|---|---|
| 固定核心和工具版本 | 让全组使用同一套零件和说明书 | 与 C 选配套 Vortex、后端、runtime、仿真器；保存 commit、子模块、补丁和真实版本 | target_lock.json 与版本记录 |
| 选择最小配置 | 先组一台容易排错的小机器 | 优先评估 RV64；从上游可用的小配置起步，核实核心数、物理线程宽度、warp 数和缓存 | 配置文件、target_caps.json |
| 跑 SimX | 在软件模型中检查程序行为 | 与 C 编译原生程序；先跑上游小样例，再接 E 的整数输入和独立答案 | 原生运行命令、输入输出、比较日志 |
| 跑 RTL 仿真 | 按电路描述的时钟过程检查真实逻辑 | 同一目标配置下跑原生 copy/vadd/affine；失败时看最小用例和必要的 trace/波形 | RTL 构建运行入口、通过与失败证据 |
| 说明能力与限制 | 告诉编译器这台机器能做什么 | 与 C/D 定逻辑线程、指针、谓词和完成语义；由 E 独立验收 | 能力表、语义用例、交接记录 |

SimX 通过说明程序在该模型中正确；RTL 仿真进一步检查电路实现。两者都需要与真实 U280 结果分开记录。所选版本若提供 SimX 纯功能模式，其周期数不能用于性能比较。[上游安装说明](https://github.com/vortexgpgpu/vortex/blob/master/docs/install_vortex.md)

**B 做什么：把核心配置实现到板卡，并验证整条数据通路。**

U280 是现成的 FPGA 加速卡。B 使用 FPGA 工具把电路设计转换成板卡可加载的硬件配置，然后与 C 一起完成“传入数据—执行—等完成—读回结果”。

| 工作 | 通俗解释 | 怎么做 | 留下什么 |
|---|---|---|---|
| 核查环境 | 确认有地方构建、有板卡运行 | 确认服务器入口、卡型/设备标识、排期、权限、内存/磁盘、工具/许可、XRT/驱动、shell/platform | 平台盘点和阻塞清单 |
| 适配平台 | 让核心接上板卡已有的接口和内存 | 沿用上游 XRT 流程，核实实际内存连接、地址映射和所需主机内存能力；与 C 验传输 | 平台配置、内存连接说明 |
| FPGA 构建 | 把电路描述变成板卡配置 | 固定输入后执行综合、布局布线和打包，保存完整日志；读取资源与时序报告 | xclbin/bitstream、构建脚本、报告 |
| 原生程序上板 | 先证明基础平台可工作 | 与 C 装载原生模块，上传数据、启动、等待并读回；与 E 答案逐项比较 | 原生板上结果、重复运行记录 |
| PTX 程序上板 | 接受队友自动编译出的程序 | C/D 交付合法模块后，在同一硬件配置下运行三类 kernel | PTX 板上结果、故障定位记录 |
| 测量和恢复 | 说明实际速度及失败后如何继续 | 分开记录传输/执行时间；核实超时后的停止、隔离与恢复能力 | 性能表、已验证恢复步骤及限制 |

上游 FPGA 指南使用 XRT 构建和运行路径；其中平台名称是示例，必须换成实际安装且与所选版本匹配的平台。当前指南还描述了硬件路径的 host-memory 需求，盘点时需核实所选版本是否依赖它，以及环境是否满足。[上游 FPGA 指南](https://github.com/vortexgpgpu/vortex/blob/master/docs/fpga_setup.md)

两种产物要分清：**xclbin/bitstream 配置 FPGA 上的硬件；kernel 程序由这套硬件执行。** 在目标能力与接口兼容时，更换 copy、vadd、affine 程序可以复用同一硬件配置；改变核心/缓存等硬件配置则需要重新构建并验证。

**用一次向量加法理解 A/B 如何合作。**

设 x=[1,2,3]，y=[10,20,30]，期望 z=[11,22,33]。C 负责应用侧分配、传入参数和启动，D 负责把 PTX 转成符合约定的程序，E 提供独立答案。你负责确认 Vortex 的线程按约定读到正确元素、执行正确运算、写回正确位置，并让这条路径在 U280 上成立。

例如测试时启动 32 个逻辑线程而 N=3，只有编号 0、1、2 应访问数组，其余线程应被条件屏蔽。A 要检查线程映射和屏蔽行为；B 与 C 要确认传输、内存连接及完成后的结果可见性。最终数组正确还不足以证明被屏蔽线程没有偷偷读内存，这类语义测试需用 trace、访问计数等可用观察手段补充。这里的 32 是测试的逻辑 block 大小，物理线程宽度由实际配置决定。

**30 天安排。**

你只有一份主动工作时间。平台核查从第一天开始，首轮 FPGA 构建在配置和依赖具备后尽早提交；利用构建等待时间做仿真、语义核对和证据整理。

| 时间 | 你的优先工作 | 完成标准 | 依赖未满足时 |
|---|---|---|---|
| D1—D3 | 与 C 选择配套版本，跑原生 SimX；同时盘点板卡环境，准备 RTL 和 FPGA 构建入口 | 原生 SimX 对答案；已核查的版本/配置可追溯；平台缺项有负责人 | 集中修原生基线；未知字段保留 draft，不写成已冻结 |
| D4—D7 | 原生 RTL 冒烟测试和边界回归；检查平台连接；条件具备则启动首轮 FPGA 构建 | 至少一个小型原生整数程序 RTL 对答案；构建已启动或明确 BLOCKED；向 C/D/E 交能力与限制 | 不扩硬件能力；D/C 的 PTX→SimX 工作继续并行 |
| D8—D14 | 完成同配置 RTL 验证；接收 PTX 三类程序做 RTL 验证；争取跑通原生 U280 | copy/vadd/affine 的原生/PTX 仿真结果逐项记录；原生板上状态单列 | 分清电路、平台、编译或 ABI 问题；基线未通过则暂停优化 |
| D15—D21 | 与 C/D/E 接通三类 PTX 程序上板；排查尾线程、重复启动、完成可见性与恢复 | 三类程序板上输出与独立答案一致；相同配置原生/PTX 可对照 | 板卡受阻则交完整仿真证据和阻塞单，U280 项继续标未完成 |

这份安排承接总计划的 G0—G5。G1 的 PTX copy/vadd 编译闭环由 C/D 主责，你提供已验证目标和必要的硬件支持；G2/G3 开始与你的 RTL/上板路径汇合。

协议中的重点接口是 V01（目标能力）、V05（平台运行）、V07（验证）、V08（AI 任务与接收）。你负责核心和平台；模块打包、host API 与 PTX 解析仍按 C/D 分工推进。线程和参数约定由 A/C/D 联合维护。

**最低验收清单。**

- 固定一组源码、工具链、配置和平台信息。能力表说明已验证范围；优先 RV64，若改 RV32，另立受限 profile 并检查地址范围。
- 原生与 PTX 两条程序路径分别覆盖 copy、vadd、整数 affine；SimX、RTL、U280 每层独立记录。
- 覆盖 N=0/1/7/31/32/33/63/64/65/257/1024，以及能力允许的不同 block 大小、尾线程、u32 溢出和固定随机输入。N=0 仍按 profile 合法启动，检查所有访存均被屏蔽。
- 全真、全假和混合谓词测试；用可用观察手段检查假谓词不发出访存。地址哨兵主要帮助发现越界写，不能单独证明不存在越界读。
- 与 C 验证完成后结果可读、连续两次不同输入不串数据，并如实记录超时/恢复能力。缺少的精确错误位置或安全中止能力写入限制。
- FPGA 产物保存哈希、实现报告和实际时钟；核查时序是否满足约束，以及资源是否可用。生成文件后仍需真实运行验收。
- 每轮保存命令、退出码、原始日志、输入输出、答案来源与版本；交给非作者独立重跑。

每轮结果放 `results/<run_id>/`。按项目既有约定，FAIL 表示已尝试但失败，BLOCKED 表示受外部条件阻塞，NOT_RUN 表示尚未执行；仅有配置文件或测试向量不能记 PASS。

**出了问题先查哪里。**

| 现象 | 优先定位 |
|---|---|
| 原生 SimX 就失败 | A/C 检查工具链、程序、版本和目标配置 |
| 原生 SimX 正确，PTX SimX 错误 | D/C 检查转换、参数与线程适配；A 核对目标语义 |
| 同一合法程序 SimX 正确，RTL 错误 | A 检查配置一致性、RTL 与仿真环境；必要时与 C/D 联查 |
| 数据传输单独失败，或原生 RTL 过但板上失败 | B/C 检查驱动、platform、硬件文件、内存连接与完成条件 |
| 原生板上过，PTX 板上失败 | C 组织 A/D 比较模块、ABI、设备代码和实际输入 |

采用最小失败用例定位首个异常位置，保留失败日志。板卡不可用时推进仿真；时序难以收敛时评估缩小规模或降低频率，变更后更新配置身份并重新验收。

**你需要掌握的知识与 AI 分工。**

先掌握五件事：能读懂一个向量 kernel；理解逻辑线程如何处理不同元素；看懂 RTL 中时钟/复位/握手/访存的基本关系；会运行构建并定位第一处错误；会区分功能正确、资源占用、时序和真实性能。按当前遇到的问题读 Vortex 的对应模块，逐步深入调度、分歧处理和缓存。

你可以让 AI 分别做版本资料整理、构建脚本、仿真用例、日志分析，再由独立审查者复核。每张任务卡写清输入版本、允许修改文件、验收命令、时间/成本预算和交付目录；实施者不修改 E 的冻结答案。你保留配置与接口决策、真实运行复核和最终接收责任。

每天用 10 分钟记录“今天新增的证据、阻塞与负责方、明天的交付”。记录人工主动时间和工具等待时间；与 E 预先选择 A/B 的 AI 成对实验任务，保留失败样本及所有子智能体成本。

首月研究贡献可以来自平台适配、可靠验证、配置对照及 AI 开发过程的可复现证据。硬件优化在基线稳定后开展，每次只改一个变量；性能按总计划采用 5 次预热、30 次测量，报告中位数与范围，分别记录传输、执行和总时间。RTL 较慢时预先声明减少重复数，仿真数据与板卡测量分开。

最终你交付：可追溯的目标配置、原生与 PTX 的仿真结果、U280 构建与上板材料、资源/时序/性能记录、限制与恢复说明，以及别人能够照着重跑的步骤。若板卡条件阻塞，完整保留已完成的仿真交付，并将 U280 目标列为未完成。
